# T01: シリアル・BCON・コントローラタブのレイアウト改善

## 依頼内容

3タブの役割と表示順を整理し、接続・設定・手動操作に必要な項目を見つけやすくする。実装担当workerは、この指示書に基づいてUIを修正し、検証結果を報告する。

この指示書を作成した時点では、コードと関連資料の読み取りだけを行っている。配置案は実画面で未検証であり、以下の図はピクセル単位の指定ではない。実際の表示幅、文字サイズ、既存の操作契約を確認して調整する。

## 作業開始時に読むもの

- ルートの `AGENTS.md`
- `docs/agents/orca-worker.md`（Orcaの統括役からこの指示書を受けた場合）
- `docs/BCON_TRANSPORT.md`
- `docs/IMU.md`
- `.opencode/skills/gui-probe/SKILL.md`（実画面の検証前）

本タスクでは実装と検証までを担当する。コミット・push・PR作成・他workerへの再委任は、依頼元から別途指示された場合に行う。Orca workerの共通手順と競合する場合、コミットについてはこのタスク固有の指定を優先する。開始時に未コミット差分を確認し、他の作業を上書きしない。

## 目的と対象範囲

| タブ | 役割 | 最初に見せる情報 |
|---|---|---|
| シリアル | PCと機器の接続 | 接続状態、通信方式、ポート、接続操作 |
| BCON | PicoとSwitchの接続・本体設定 | PC側とSwitch側の状態、現在のモード、主要操作 |
| コントローラ | 手動入力の設定と操作 | 入力受付状態、有効な入力元、仮想コントローラ |

今回の中心は配置、情報の優先順位、表示名、折りたたみ、幅への追従である。通信プロトコル、接続の自動化、入力の優先制御そのもの、保存形式は変更しない。既存機能への到達経路を残す。

## 共通レイアウト規則

1. 各タブを「状態 → 主要操作 → 詳細設定」の順に揃える。
2. 狭い幅では1列にし、主要操作に横スクロールを要求しない。ウィンドウの最小幅を引き上げて解決しない。
3. ラベルの開始位置、入力欄の幅、ボタンの高さ、余白を揃える。既存テーマを使用し、固定色や独自装飾を増やさない。
4. 長い機器名、状態文、エラー文は折り返す。状態更新のたびに主要ボタンが大きく移動しないようにする。
5. 日常操作を上部にまとめる。詳細には縦スクロールを許容する。上部の固定表示は既存構造で無理なく実現できる場合に限り、必須条件にはしない。
6. 詳細は少数の折りたたみで整理し、タブの中にさらにタブを増やさない。開閉しても入力値・選択状態・ログを破棄しない。
7. 無効な操作の理由を近くに文字で示す。色やツールチップだけに依存しない。Tabキーの移動順を表示順に合わせる。
8. 初回表示では診断・保守を閉じる。セッション中の開閉状態は保持する。新しい永続設定は追加しない。

## シリアルタブ

### 配置案

```text
[接続状態：接続済み / COM3 / BCON]       [切断]

通信方式  [方式の表示名                 v]
ポート    [COM3：機器名                 v]
                              [一覧更新]
[接続 または 再接続]
操作結果・失敗理由・必要な復旧操作

Switch側：状態の要約          [BCON設定へ]

> 通信の詳細設定
> 診断・送信ログ
```

- 常時表示する接続情報は簡潔にし、選択値と実際の値、HELLOなどの診断情報は詳細欄へまとめる。両者が異なる場合や失敗時は、差異・原因を基本表示にも出す。
- 通信方式をポートより前に配置する。表示名を改善する場合も内部キーとの対応を保ち、登録された未知の方式を候補から落とさない。
- 通信速度は現在値を確認できるようにし、変更欄を詳細にまとめる。「速度を探す」はBCONの適用条件に従い、失敗時にも見つけられる導線を置く。
- 「送信内容を表示」は診断欄へ移す。
- 「入力調停」はコントローラタブへ移す。既存の設定変数・候補・適用処理を利用する。
- LED・振動の詳細はBCONタブへ集約する。シリアル側にはSwitch側状態の要約とBCONタブへの導線を残す。
- 接続中の切断、未接続時の接続、接続済み時の再接続を維持する。ボタンの統合で既存の操作を失わせない。
- PC側のポート接続、BCONの応答確認、Switch側の状態を混同しない。取得できない状態は「不明」とする。

## BCONタブ

### 配置案（狭い場合）

```text
PC ↔ Pico：接続状態
Pico ↔ Switch：確認できた状態
現在のモード：有線/無線、コントローラ種別

[状態を更新] [Switchへ再接続]
操作中の表示・結果・次の操作

v 接続モード・ペアリング
  接続方式、種別、取込時間、取込・再生操作
  前提条件と操作順の説明

コントローラ状態（LED・振動など）
> 本体色
> 通信診断・詳細ログ
> 保守
```

- 幅が広い場合は左列に操作、右列に状態・ログを配置してよい。狭めると1列へ戻り、広いときの要求幅が残らないようにする。主要な手順は左列だけで追える配置にする。
- 現在ある接続、ペアリング、モード、状態、色、速度、ログ、保守の機能を保持し、枠の入れ子を減らす。
- 「再接続」は対象を明示する。PC側への接続操作とSwitch側への再接続操作を区別する。
- HELLO再試行、PING、速度探索は通信診断へまとめる。ただし接続失敗時は適用可能な復旧操作への導線を基本表示にも出す。
- ペアリングは「前提確認 → 取込 → 保存結果確認 → 再接続」の順に読めるようにする。既存サービスの結果から確認できる段階だけを表示し、新しい自動実行フローは作らない。
- モード変更による再起動の影響を操作前に示す。再起動後に必要なポート更新・接続への導線を置き、自動再接続は追加しない。
- 本体色は展開時に編集でき、未送信の下書きを保持する。
- 保守は最下部の折りたたみにまとめる。BOOTSEL・取込破棄・鍵削除の既存確認を保持する。
- 操作結果は該当欄の近くに表示する。詳細ログは追跡用とし、結果確認のたびにスクロールさせない。
- BCON以外の方式へ切り替えた際のタブ非表示と、再表示時の下書き・ログ保持を維持する。

## コントローラタブ

### 配置案（狭い場合）

```text
送信先：接続状態
手動入力：受付状態と制限理由

[ ] キーボードで操作
    操作方法・既存の割り当てを確認する導線
[ ] ゲームパッドで操作
    [パッド名                          v]
    読み取り状態                [再接続]
    必要な場合だけ初期設定への案内
> マウス操作
> コマンド実行中の手動入力・調整

仮想コントローラ                 [別窓へ]
    ボタン・スティックの操作領域

ジャイロ：状態                 [開始/停止]
> ジャイロ設定
```

- パッド選択・再接続・遊び・HidHideを横一列に詰めない。パッド名を表示する幅を確保し、調整項目は詳細へ移す。
- 「遊び」は「スティックの遊び」と表示する。割合表示を採用する場合は既存の生値・保存値との換算を確認する。単位が不明なまま数値を置き換えない。
- キーボード・ゲームパッド・マウスの有効設定と状態を対応づける。併用できる入力を排他的な選択肢に変更しない。
- 入力調停は「コマンド実行中の手動入力」として配置し、各候補が意味する動作を既存実装に基づいて説明する。
- 「設定が有効」「機器から読取中」「Switchへの入力が許可されている」を混同しない。情報が取得できない場合は推測で正常表示しない。
- HidHideが必要な場合は、無効な入口の近くに理由とセットアップボタンを表示する。OS別の既存条件を保持する。
- キー割り当てやマウス操作の案内は現行実装に合わせる。新しい割り当て編集機能は追加しない。
- 仮想コントローラの操作領域を優先し、設定欄に押し下げられすぎないようにする。広い場合は設定と操作領域を左右に配置してよい。
- 別窓化とタブへの復帰、切替時の押しっぱなし解除、ジャイロパネルの同行を維持する。
- ジャイロは状態と開始・停止を基本表示に置く。入力源などは詳細へまとめる。折りたたみ・タブ切替だけで開始や停止を行わない。

## 実装上の制約

- 接続表示の根拠は `SerialService.connection_snapshot()` とする。UIから接続状態を独自に推定しない。
- Tk操作はGUIスレッドで行う。既存のUiInbox、世代判定、可視性判定を保持する。
- 更新頻度や通信処理を増やさない。新しい `after(1)` チェーンを追加しない。
- 折りたたみのために通信購読や入力機能を重複生成しない。ウィジェットの再作成による状態消失を避ける。
- コマンド実行中・接続処理中の操作制限と、緊急切断の動作を維持する。
- BCONの未受信・更新停止表示を保持し、古い値を現在の正常状態として表示しない。

## 作業手順

1. 現行コード、関連テスト、未コミット差分を確認する。指示書作成後に変更が進んでいる場合は現在の実装を基準にする。
2. 現行GUIの幅と高さ、3タブの配置を確認し、比較用の画像を保存する。実画面確認ができない場合は制約を報告する。
3. 共通の余白・折りたたみ・幅への追従を決め、シリアル、BCON、コントローラの順に変更する。
4. 関連テストを実行し、実際の表示と操作を確認する。必要な回帰テストを追加する。
5. 全体ゲートを実行し、完了報告を作成する。

## 検証と完了条件

### レイアウト確認

- 3タブそれぞれで、狭い幅と広い幅、詳細の開閉を確認する。まずタブの可視幅360px前後と640px前後を目安にし、実際の可視幅を記録する。
- 狭い幅で主要ボタン・入力欄が欠けず、操作のための横スクロールが不要である。
- 長い機器名・失敗理由でも重なりがない。詳細を開閉しても値やログが失われない。
- 未接続、接続処理中、接続済み、失敗、コマンド実行中を確認する。疑似状態を利用した表示確認は実通信検証と区別して報告する。
- BCONの表示・非表示、仮想コントローラの別窓化・復帰、ジャイロ設定の開閉を確認する。
- マウス操作に加え、Tabキーで主要操作へ到達できることを確認する。
- 実画面確認では専用プロファイルを使う。既存利用者のアプリを終了させたり、使用中の実機を取得したりしない。gui-probeの例にある固定パス・機器番号をそのまま使わず、現環境を確認する。

### 自動検証

- 変更したPythonファイルに `uv run --frozen python -m py_compile <対象ファイル>` を実行する。
- 関連する接続表示、BCONレイアウト・タブ、コントローラドック、ゲームパッド、IMUの既存テストを実行する。例：`test_bcon_connection_views.py`、`test_bcon_layout_contract.py`、`test_bcon_tab_contract.py`、`test_controller_dock_contract.py`、`test_hidhide_gamepad_gate.py`、`test_gamepad_list_refresh.py`、`test_imu_panel.py`。
- テストを修正する場合は、新しい表示契約に対応させる。状態保持や操作制限のアサーションを削除して通さない。
- 最終的に `task ci` を実行する。Taskがない場合は `taskfile.yml` の対応するコマンドを実行する。
- 既存失敗や環境制約がある場合、原因・変更との関係・未実行項目を記録する。無関係な修正へ範囲を広げない。

完了には、対象機能への導線が保持され、レイアウト確認と必要な自動検証が済んでいることが必要である。実画面未確認の場合は「見た目の受入確認待ち」とする。機器なしの表示確認で、実機接続・ペアリング・ジャイロの成功を報告しない。

## 完了報告

`docs/tasks/T01-connection-controller-layout-report.md` に以下を記載する。

- タブごとの変更内容と、その理由
- 変更ファイルと主要箇所の行番号
- 変更前後の画像の保存先、確認した可視幅・表示倍率・状態
- 実行した検証コマンド、終了結果、テスト件数
- 未確認事項、実機検証の有無、残っている問題
- 指示書から調整した点と根拠

Orca経由で割り当てられた場合は、利用可能なOrcaの報告手順に従って依頼元へ完了または未完了を通知する。完了した指示書と報告のアーカイブは、依頼元が受入確認した後に行う。
