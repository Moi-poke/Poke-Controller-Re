## 2. 高さ条件：「本文 666px」を撤回し、「パッド下端が見える」に変更

前回は「本文 666px 以上」と書きながら「720 は可」としており、720 の本文は **653px**（タブ枠 684 − 見出し 31）で、666px に届いていなかった。原因は「コントローラタブの全内容（635px）が収まるか」を条件にしたこと。HidHide の案内行の有無で結果が変わるため、条件として不適切。

### 新しい条件

**「パッドの下端までが見えること」**にする。折りたたみ（マウス操作 / ゲームパッドの調整 / コマンド実行中の手動入力）やジャイロ設定が見切れるのは許容する。

パッドを「キーボード / ゲームパッド」の直下へ移した場合の必要高さ（125%）:

| 要素 | 高さ |
|---|---|
| キーボード行 | 約 30 |
| ゲームパッド行 | 約 30 |
| パッド選択行 | 約 30 |
| 仮想コントローラ枠（見出し + パッド 202 + 余白） | 約 240 |
| 余白 | 約 6〜16 |
| 合計 | **約 336〜346** |

- **720（本文 653）**: 可。余裕は約 307〜317px。
- **600（本文 533）**: 可。余裕は約 187〜197px。全体はスクロールするが、パッドは見える。
- **480（本文 413）**: 可。ただし 640 幅ではフォールバックするため、実際は `log_right` + ログ非表示側。
- **640 幅**: 幅の条件で `tabs_right` 不成立。高さ以前の問題。

前回の「1024×600 では 92px 足りない」は、**全内容 635px を条件にした場合**の話（正しくは本文 533 で 102px 不足）。パッド下端条件なら 1024×600 は可。訂正する。

高さは**設計時に一度確認する条件**で足りる。最小 480 でも本文 413 に対しパッド下端は約 336〜346。実行時の高さによる自動切り替えは不要。HidHide の案内行がパッドより上に出る場合だけ、+30px を見込む。

## 3. 自動切り替えの仕様（追加レビューの 4 点をすべて決める）

自動切り替えは `tabs_right` のときだけ。設定の `arrangement` と `show_log` は変更しない（**実効レイアウトだけ**を切り替える）。

| 項目 | 仕様 |
|---|---|
| 対象 | ユーザーの設定が `tabs_right` のときだけ。他の配置では何もしない。 |
| 幅の下限 | `right_min` は**論理pxで 415**（=ceil(420×0.9+36.8)）。物理は 100% 415 / 125% 519 / 150% 623（切り上げ）。`pad_req_logical = canvas.winfo_reqwidth() / factor`、`factor = winfo_fpixels("1i") / 96`（125%で1.25。**Tk scaling の1.666は1ptあたりpxなので使わない**）。1:1 は論理 457（物理 571 / 685）。実測の右列 523 物理は 91% で下限を満たす。 |
| 左列の下限 | **論理px**。`left_min = 380` を推奨（映像 380×214 論理）。480 にすると 1024×600@125%（819 論理）と 1280×720@150%（853 論理）が `right_min+480` を割り、`tabs_right` にできない。400 でも 1024@125 は sash 6px を引くと 399 論理で 1px 足りない。 |
| フォールバック開始 | **論理幅** `W_logical < right_min_logical + left_min + sash_logical`。`left_min=380`、`sash≈4.8`、`right_min≈415` の 125% で約 **800**（物理 1000）。**この値は実行時計算で、800 は例**。 |
| 復帰 | 上記の実行時しきい値 + **40 論理px**（125%で約 840 / 物理 1050）。 |
| 起動時 | ヒステリシスは使わず、`W_logical >= runtime_threshold` なら `tabs_right`、未満ならフォールバック。帯の中なら `tabs_right` で開始。 |
| デバウンス | 最後の `<Configure>` から **150ms** 待って判定。連続リサイズ中は組み替えない。 |
| DPI 変化 | 計測では `SetProcessDPIAware` を呼び、Tk scaling 1.666（=120dpi/72）の**システム DPI 対応**として動いている（GDI surface にも同じ呼び出しがある）。拡大率は `factor = winfo_fpixels("1i")/96`（125%で1.25）。システム DPI 対応ならモニタ移動で `winfo_fpixels` は変わらず、再計算不要。**per-monitor DPI の場合だけ** `WM_DPICHANGED` を受ける。実装時に `GetProcessDpiAwareness` で確認する。 |
| 保存しないもの | 実効配置、実効ログ表示、フォールバック時の仕切り位置。`arrangement` / `show_log` / `pane_sashes` は触らない。 |
| 仕切り位置の保護 | 一時切り替えで `PaneArranger` を組み直すとき、`remember_sashes` を**抑制**する。抑制しないと、フォールバック形の比率が保存済みの形を上書きする。 |
| ログの復元 | 自動で隠した場合だけ戻す。ユーザーが元々ログを隠していた場合は、その設定を維持する。 |
| 右列幅の保存 | **論理px**（物理px ÷ `factor`）。125% の 523px は 418 として保存し、復元時に ×1.25 する。 |
| 手で仕切りを動かした | 左列の上下仕切り: ドラッグ後は**ログの高さ `log_h` を論理pxで保存**し、自動のログ高さ計算を停止（仕切りの上端位置ではなく、ログの高さを保存する）。「仕切りを既定の位置に戻す」で解除。右列: `right_min` 未満へはドラッグ不可。 |
| 一時切り替え中 | 仕切りドラッグは無効化（または無視）。`remember_sashes` は抑制。 |
| 表示上の扱い | メニューは `tabs_right` を選択したまま。狭いため一時的にフォールバックしている旨を、状態バーかツールチップに出す（任意）。 |

### 実装上の注意

- 現在の `PaneArranger.remember_sashes()` は、配置を組み直すたびに比率を控える。自動切り替えで形が変わると、`log_right` の比率を上書きし得る。**一時切り替え中は控えない**フラグが必要。
- `show_log` を `setPaneVisible` で false にすると保存される。自動側は `arrangement_tree(..., show_log=False)` へ直接渡し、設定変数は触らない。
- 定数にしてよいのは `left_min`・ヒステリシス（40 論理px）・縮小率（0.9）だけ。`right_min` と `W_fallback` は実行時に `pad_req` と sash から計算する（800/840 は 125% の例）。

## 4. ログの高さ：「重み 4:1.5」ではなく、映像の必要高さから残りを回す

追加レビューの指摘どおり、重みで近似するより、**映像に必要な高さを計算して残りをログへ**回す方が崩れない。

### 計算

1. 左列幅 `left_w`（1280 で約 741、1920 で約 1390）
2. プレビュー内側 `preview_w = left_w - 14`
3. 16:9 の映像高 `video_h = preview_w × 9 / 16`
4. カメラ枠の必要高 `camera_h = video_h + 66（ツールバー等）+ 30（実行バー）`
5. `log_h = total_h - camera_h`。`log_h < 180` なら `log_h = 180`、`camera_h = total_h - 180`
6. 仕切りは `camera_h` の位置へ置く（比率ではなく px。DPI 変更時は再計算）

### 数値

| ウィンドウ | 左列幅 | 映像 | ログ | 備考 |
|---|---|---|---|---|
| 1280×720 | 741 | 727×409 | 約 179 → 180 | 映像は横幅で決まる |
| 1920×1080 | 1390 | **1365×768** | **180** | 先にログ最小 180 を確保。映像は 768 高で頭打ち |
| 2560×1080 | 2030 | 高さで頭打ち | 180（最小） | 映像が高さで決まる領域 |

数値は 125% の実測/計算。実装では `96`（ツールバー等）と `180`（ログ最小）を固定値にせず、ウィジェットの要求高から測る。

**訂正（前回の数値）:** 1920 で「映像 1376×774 とログ 180」は同時に成り立たない。必要な高さは 774+96+180=1050 で、使える 1044 を超える。正しくは、ログ 180 を先に引くとカメラ枠 864、映像の高さ 768、幅 1365。したがって 1920×1080 でも**わずかに高さで頭打ち**になる。

高さで頭打ちになる左列幅のしきい値は、固定の 1685px ではなく、式で決まる:

```
video_h_max = total_h - chrome(96) - log_min(180)
video_w_max = video_h_max * 16 / 9
left_w_threshold = video_w_max + 14
```

1920×1080（125%）では `(1044-96-180)=768`、`768*16/9=1365`、`+14=1379`。左列が 1379px を超えると高さで頭打ち。

それでも「映像の必要高さを計算し、残りをログへ」という規則は正しい。1920 ではログが最小 180px になり、1280 では約 180px になる。

## 6. 残る実測

- 100% / 150% DPI で、`right_min`（論理 415 / 物理 415・519・623）とパッドの可読性。
- パッドを上へ移した実際の `pad_bottom`（推定 336〜346 / 125%）。
- `tabs_right` + 実行バーを入れた 1280×720 の実画面（映像 727×409、ログ 180、右列 523）。
- 640 / 1024 / 1280 / 1920 の切り替えヒステリシス（実行時しきい値。125% の例で論理 800 / 840、物理 1000 / 1050）。
- 640 のフォールバックに実行バーを出した状態で、接続 / 切断がまだ見えるか（現行の y=370 はバーなしの実測。バー 30px で約 171px に縮む見込み）。
- ログのピン留めを畳んだ状態で、✖ / ⚠ の件数がクリックできること。

これらを測るまでは、`tabs_right` を既定にしない。設計としては、幅・高さ・DPI の条件を入れておけば、どの DPI でも既定にできる形になる。
